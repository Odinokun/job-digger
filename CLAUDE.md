# Job Digger - правила роботи над проєктом

Персональний застосунок для пошуку кар'єрних сторінок компаній, моніторингу вакансій і показу нових вакансій. Масштаб - від десятків до 300+ компаній.

**Джерело правди щодо вимог - технічний план у `docs/`**, карта розділів: [docs/README.md](docs/README.md). Цей файл не дублює план, а збирає правила роботи й дає орієнтир в архітектурі. Якщо тут і в плані різне - правий план, а розбіжність треба виправити.

**Джерело правди щодо стану задач - дошка Trello «JD - Job Digger»**: https://trello.com/b/8UsxKeak/jd-job-digger. Перелік обсягу робіт - [.claude/plans/job-digger-tasks.md](.claude/plans/job-digger-tasks.md) (статичний довідник, галочки в ньому не проставляються).

## Стек

| ------------ | ------------------------------------------------------------- |
| Фреймворк    | Next.js 16, App Router, Turbopack                             |
| Мова         | TypeScript                                                    |
| UI           | HeroUI v3 (3.2.x) + Tailwind CSS v4                           |

Next.js 16 має зміни проти тренувальних даних моделей: документація встановленої версії лежить у `node_modules/next/dist/docs/`, читай її перед написанням коду (про це ж нагадує `AGENTS.md`, який генерує `next dev`).

Те саме з Drizzle, але навпаки: встановлена стабільна 0.45.x, а сайт orm.drizzle.team документує лише v1 (RC), архіву для 0.x немає. API звіряй із типами в `node_modules/drizzle-orm/`. Деталі роботи з базою - [src/server/db/README.md](src/server/db/README.md).

Проєкт на ESM, службові скрипти виконує сам Node 26 без збирача - деталі й наслідки для імпортів у [README](README.md#стек) і [src/server/db/README.md](src/server/db/README.md).

## Структура репозиторію

Один репозиторій, один застосунок Next.js: фронтенд (сторінки, компоненти, HeroUI) і бекенд (Server Actions, API-маршрути обробника розкладу, черга, парсери, модуль запитів, робота з БД) разом, розведені по папках. Мультипакетний монорепозиторій (Turborepo, pnpm workspaces) не потрібен.

- `src/app` - сторінки, layout, компоненти, маршрути App Router. Деталі - [src/app/README.md](src/app/README.md).
- `src/server` - Server Actions, робота з БД, черга, парсери, модуль HTTP-запитів. Деталі - [src/server/README.md](src/server/README.md).
- `src/i18n` - налаштування next-intl: список мов і читання локалі з cookie. Самі переклади - у `messages/` у корені.
- `docs/` - технічний план.

Модулі з `src/server` не імпортуються в клієнтські компоненти напряму. Імпорт-alias: `@/*` → `./src/*`.

## Архітектура

- **Одне кар'єрне джерело = одне завдання.** Компанія з трьома джерелами дає три завдання. Прогрес, помилки і Retry рахуються по джерелах.
- **Черга живе в PostgreSQL**, не в пам'яті Next.js: завдання захоплюються так, щоб два процеси не взяли одне й те саме, а завислі повертаються в чергу. Локально - фоновий цикл у сервері Next.js, на Vercel - функція до 4,5 хв, яка перезапускає себе.
- Одночасно виконується не більше 5 джерел - спільний ліміт для всіх користувачів, задається через ENV.
- Одна загальна перевірка одночасно на користувача. Деталі - [docs/checks-and-queue.md](docs/checks-and-queue.md).

Таблиці: `users`, `companies`, `career_sources`, `vacancies`, `check_runs`, `check_tasks`, `settings` ([docs/data.md](docs/data.md)). Для локальної версії - один системний користувач, але дані завжди ізольовані за користувачем.

Екрани: **Jobs** (Unread / Read / Favorites / All), **Companies** (Tracked / Not tracked), **History**, **Settings** ([docs/ui.md](docs/ui.md)).

## Як працюємо: маленькі кроки

- Кожна задача ділиться на маленькі кроки. Один крок - одна невелика зміна (зазвичай «один тест + код, що робить його зеленим») і один коміт.
- **Перед кроком** - коротке пояснення українською: що робимо і навіщо, які файли зміняться, які нові поняття з'являться (з поясненням при першій появі і посиланням на офіційну документацію). Код пишеться лише після «ок» або відповідей на питання.
- **Після кроку** - що змінилося, як перевірити і запропонований англійський текст коміту.
- **Коміт - лише після перегляду автором.** Не комітити одразу: показати текст коміту і чекати. Автор сам передивляється змінені файли і дає окреме «ок» саме на коміт. «Ок» на крок дозволяє писати код, але не комітити його.
- Питання про погодження кроку - фразою **«Hit the road, Jack?»**.
- **Вибір - вкладками, а не списком у тексті.** Коли рішення за автором і варіантів кілька, Claude питає інструментом `AskUserQuestion`: вкладки з варіантами, де перший позначений як рекомендований, а в кожного описано, що він означає і в чому компроміс. Це стосується і розвилок у коді, і дрібниць процесу - чи потрібна картка, куди покласти зміну, що робити з гілкою. Якщо варіант один або рішення очевидне - робимо й повідомляємо, без питання.
- Темп можна змінити будь-коли («пояснюй коротше», «ці кроки можна об'єднати»).

## Документація

- **Документація оновлюється разом зі зміною, а не потім.** Будь-яка зміна в проєкті чи нова фіча - це ще й правка документації: `CLAUDE.md`, коренева `README.md`, README поруч із кодом, технічний план у `docs/`. Перед кожним комітом перевіряй, чи щось із цього не стало неправдою.
- **Без дублювання.** Кожен факт живе в одному місці. Якщо його треба згадати ще десь - посилання, а не копія.
- **План у `docs/` - тимчасовий.** Він створений для розробки і в кінцевому проєкті лишатися не повинен. Коли зроблена частина плану переїжджає в код, тести, `CLAUDE.md` або README поруч із кодом - відповідний текст із плану видаляється. Умова одна: видаляти лише тоді, коли знання справді є в іншому місці, а не просто тому, що картка в Done.
- **Куди зростає документація далі:** `CLAUDE.md` - правила й орієнтири; README у відповідній теці - деталі конкретної частини коду. Нові файли документації кладуться поруч із тим, що вони описують, а не в спільну теку.

## Мова

- **Українською:** документація (`docs/`, README, описи задач і PR) і коментарі в коді. Згодом їх можуть перекласти англійською.
- **Англійською:** коміти, назви в коді (змінні, функції, файли, таблиці й колонки БД), назви тестів, логи й технічні повідомлення про помилки.
- **Тексти інтерфейсу** - англійською й українською через ключі next-intl у двох файлах перекладів. Тест перевіряє, що ключі однакові. Дані із сайтів (назви вакансій і компаній, локації) не перекладаються.
- Мова не в URL: next-intl без i18n-роутингу, локаль із cookie, бо за планом мова - особисте налаштування користувача. Деталі - [README](README.md#локалізація), код - `src/i18n/`.

## Тести і TDD

- **Логіка - строго за TDD:** спершу тест, який падає, потім код. Це парсери, правила життєвого циклу вакансій, очищення URL і дублікати, захист від SSRF, розрахунок наступної автоперевірки, CSV, черга.
- **Верстка й дрібниці UI** - без строгого TDD.
- **E2E - TDD на рівні етапу:** сценарій пишеться на початку етапу як критерій готовності (червоний) і має бути зеленим наприкінці.
- Три рівні: Vitest (чиста логіка), Vitest + PostgreSQL в Docker на окремій тестовій базі (черга, умовне видалення, одночасні зміни), Playwright Test (5-7 ключових сценаріїв).
- **Тести ніколи не ходять на справжні сайти.** Замість них - локальний фейковий сервер зі збереженими відповідями платформ; для кожного парсера зберігається реальна відповідь платформи у файлі. У тестовому режимі захист від SSRF дозволяє лише адресу фейкового сервера.

Назви файлів розділяють рівні: `*.test.ts` - юніт-тести (проєкт Vitest `unit`), `*.integration.test.ts` - тести зі справжньою базою (проєкт `integration`). Запуск: `npm test` (усе), `npm run test:unit`, `npm run test:integration`, `npm run test:watch`.

E2E живуть окремо від Vitest: тека `e2e/`, файли `*.spec.ts`, конфіг `playwright.config.ts`, запуск `npm run test:e2e` (і `npm run test:e2e:ui`). `npm test` їх не зачіпає, бо вони піднімають застосунок. Браузер лише Chromium, сервер для тестів запускає сам Playwright - деталі в [README](README.md#e2e-тести).

Інтеграційним тестам потрібні піднята база (`docker compose up -d`) і змінна `TEST_DATABASE_URL` - окрема база, не база розробки. Деталі обвʼязки й рішення щодо ізоляції - [src/server/db/testing/README.md](src/server/db/testing/README.md).

`globals` у Vitest вимкнені: `describe`, `it`, `expect` імпортуються явно з `vitest`.

## Git і Trello

- `main` завжди робочий, напряму в `main` нічого не комітимо.
- Одна картка Trello = одна гілка. Назва гілки - тип і коротка суть англійською: `feat/greenhouse-parser`, `fix/duplicate-detection`.
- Коміти **і назви PR** - у форматі [Conventional Commits](https://www.conventionalcommits.org/) англійською: `feat:`, `fix:`, `test:`, `docs:`, `chore:`. Назва PR важлива саме так само, як назва коміту: при squash merge GitHub робить із неї коміт у `main`. Номер задачі й назва картки живуть в описі PR, а не в заголовку: `feat: scaffold Next.js app with TypeScript`, не `1.01 Каркас Next.js + TypeScript`.
- **Без згадок авторства Claude** у комітах і описах PR: ніяких `Co-Authored-By` і «Generated with Claude Code».
- Задача готова і її тести зелені → Pull Request з описом українською, картка переходить у Testing. Опис PR обов'язково містить що зроблено, посилання на картку і розділ «Як перевірити» з конкретними командами й очікуваним результатом.
- Рев'ю, ручну перевірку і squash merge в `main` робить автор. Після злиття гілка видаляється, картка переходить у Done. Локальну гілку прибирає Claude одразу після merge: squash merge не позначає її як злиту, тому `git branch -d` відмовляється - перед `-D` Claude перевіряє, що `git diff main..<гілка>` порожній, тобто вміст гілки справді в `main`.
- Колонки дошки: **Analyze** (ідеї, що виникли під час розробки, але ще не продумані й не внесені в план - після обговорення переходять у Backlog) → **Backlog** (усі задачі з плану) → **To Do** (взяті в найближчу роботу) → **In Progress** (лише одна задача за раз) → **Testing** → **Done**. У **Testing** код готовий і автор перевіряє вручну; тести зелені, якщо задача їх передбачає - інфраструктурні задачі (каркас, службові файли, конфігурація) тестів не мають, і для них критерій це ручна перевірка за описом у PR. Одна картка - одна задача. Маленькі кроки задачі - чекліст усередині картки, етап задачі зазначений першим рядком опису («**Етап 1 — Основа проєкту**»), мітки Trello не використовуються, опис - українською. Під час роботи картка переноситься в In Progress і відмічаються пункти чекліста. Нові картки створюються лише після «ок» автора.
- GitHub Actions запускає лінт і тести на кожен PR і на push у `main`. PR із червоними тестами не зливається - але це дисциплінарне правило: для приватного репозиторію на тарифі Free GitHub не дає вимушувати перевірки, тому merge блокує лише погляд на вкладку Checks. Що саме виконується, як відтворити прогін локально і що робити при зміні тарифу - [README](README.md#ci).

## Безпека

- **Сервер лише з цього комп'ютера:** `next dev` і `next start` запускаються з `-H 127.0.0.1`.
- **Усі зміни даних - через Server Actions** (вбудована перевірка походження запиту). Для звичайних API-маршрутів перевірка Origin додається вручну.
- **Захист від SSRF:** лише http/https, внутрішні адреси (localhost, 192.168.x.x, 10.x.x.x тощо) заборонені, зокрема після редиректів. Для кожного запиту - тайм-аут і ліміт розміру відповіді.
- **Вміст із сайтів - лише як текст**, не HTML. Посилання - з `rel="noopener noreferrer"`.
- **CSV-експорт без формул:** значення, що починаються з `=`, `+`, `-` або `@`, екрануються.
- **Секрети лише в ENV**, файли `.env*` не потрапляють у git. Виняток - `.env.example`: він у git і є **єдиним переліком змінних середовища**. Нова змінна додається в `.env.example` із коментарем у тому самому PR, що вводить її в код; значення в прикладі - placeholder, не справжній секрет. Перелік не пишеться наперед: імена змінних визначає код, що їх читає.
- Ввічливість до сайтів: до 2 запитів одночасно на сайт, пауза 2 с, тайм-аут 20 с, чесний User-Agent, повага до 429, повтори лише при збоях. Захист сайтів не обходимо.

Повні правила - [docs/security.md](docs/security.md) і [docs/discovery-and-parsing.md](docs/discovery-and-parsing.md).

## Залежності й інструменти

- Нова залежність, плагін, фреймворк або шар абстракції - лише з обґрунтуванням: що вже покриває цю потребу і в чому компроміс. Нічого не додавати мовчки.
- Поведінку бібліотек, API і CLI не відтворювати з пам'яті - перевіряти в офіційній документації і давати посилання. «Не перевірив» - нормальна відповідь, вигадана - ні.
- **Install-скрипти залежностей схвалюються явно.** Пакет, який виконує свій скрипт під час установки, спершу переглядається, а тоді схвалюється через `npm install-scripts approve` - схвалення з версією живе в полі `allowScripts` у `package.json`. Команди й наслідки - [README](README.md#install-скрипти-залежностей).
- **Форматування автоматичне.** Хук `PostToolUse` (`.claude/hooks/format-file.sh`) після кожного Write/Edit у файл проєкту проганяє на ньому Prettier і `eslint --fix`; невиправні помилки ESLint блокують крок і показуються одразу. Файли поза коренем проєкту хук пропускає. Руками `npm run format` викликати не потрібно. Prettier також сортує класи Tailwind (`prettier-plugin-tailwindcss`): порядок класів у `className` не обговорюється на рев'ю, його задає плагін. Опція `tailwindStylesheet` у `.prettierrc` вказує на `src/app/globals.css` - без неї плагін не бачить токенів із `@theme` і виносить такі класи на початок.
- **Класи Tailwind перевіряє ESLint** (`eslint-plugin-tailwindcss`, конфіг `recommended`): друкарська помилка в класі - `no-custom-classname`, суперечливі класи типу `p-2 p-3` - `no-contradicting-classname` (це error, він блокує крок), а `enforces-shorthand` і `enforces-canonical-classname` пропонують коротший запис. Правило `classnames-order` вимкнене: порядок класів - робота Prettier. Налаштування `cssConfigPath` у `eslint.config.mjs` вказує на `src/app/globals.css` і для Tailwind v4 обовʼязкове.
- Власні класи HeroUI (`button--primary` і подібні) ESLint вважає невідомими і дає warning. Це нормально: у `className` ми пишемо утиліти Tailwind, а не внутрішні класи бібліотеки. Якщо колись знадобиться писати їх руками - у правило додається `whitelist`.

## Дозволи Claude Code

Permissions живуть у `.claude/settings.json` поруч із хуками - у git, бо це правило проєкту, а не особиста звичка. Переглянути й змінити інтерактивно - команда `/permissions`.

- **`allow`** - те, що Claude виконує без питання: прогін тестів, лінт, `format:check`, `build`, `db:check`, `tsc`, `prettier`, `eslint`, `playwright`, `docker compose ps/logs` і **читальні** інструменти Trello (`mcp__trello__trelloRead*`).
- **`deny`** - заборонено повністю: `rm -rf`, `git push --force`, `git reset --hard`, `git clean`, `docker compose down -v` (стирає том із локальною базою) і читання `.env*` інструментом Read.
- **`ask`** порожній свідомо: без правила Claude Code і так питає. `ask` потрібен лише щоб повернути питання там, де дозвіл уже дано.

Чого в `allow` немає навмисно: `git commit`, `git push`, `gh pr`, встановлення залежностей і **записувальні** інструменти Trello. Це або зміна історії, або дія назовні - вони лишаються з питанням. Правило «коміт лише після перегляду автором» тримається саме на цьому.

Деталі синтаксису - [документація Claude Code](https://code.claude.com/docs/en/permissions). Коротко, що варто знати при правках:

- Порядок перевірки - `deny`, потім `ask`, потім `allow`; перший збіг виграє, і `allow` не робить винятку з `deny`.
- `ls`, `cat`, `grep`, `head`, `find` і read-only `git` дозволені за замовчуванням, вносити їх не потрібно.
- У складеній команді кожна частина має бути дозволена окремо, тож `allow` на тести не відкриває `npm test && rm -rf /`.
- Правила, що намагаються обмежити **аргументи**, крихкі: `docker compose down -v` ловиться, а інший запис того самого прапорця - ні. Тому поруч стоїть і `--volumes`.
- Списки з різних файлів налаштувань не заміщаються, а складаються.

## Хуки Claude Code

Налаштування - `.claude/settings.json`, скрипти - `.claude/hooks/`. Усе в git: зміна хука проходить рев'ю так само, як зміна залежності, бо хуки виконуються автоматично з правами автора.

| Подія         | Що робить                                                                          |
| ------------- | ---------------------------------------------------------------------------------- |
| `PreToolUse`  | `protect-files.sh` блокує Write/Edit у `.env*` (крім `.env.example`), `package-lock.json` і міграції в `drizzle/` |
| `PostToolUse` | `format-file.sh` проганяє Prettier і `eslint --fix` на зміненому файлі проєкту     |
| `Notification`| `notify.sh` показує системне повідомлення, коли Claude чекає на ввід                |

- Новий скрипт у `.claude/hooks/` обов'язково з бітом виконання (`chmod +x`): без нього хук падає беззвучно, і захист лише здається налаштованим.
- `protect-files.sh` блокує тільки Write/Edit, не `Bash`. Лок-файл і секрети це від команд у терміналі не захищає.
- Повідомлення хуків ідуть у stderr: те, що хук пише в stdout, до Claude не доходить.
- `format-file.sh` пропускає файли поза коренем проєкту: там немає `eslint.config.*`, ESLint виходить із кодом 2 і крок виглядає як невдалий, хоча файл записано. Перевірка живе в скрипті, а не в полі `if` хука, бо `if` тримає рівно одне permission-правило - одним правилом не покрити і `Write`, і `Edit`.

- Скіли ставляться **лише в проєкт** через `npx skills add`, не через `curl | bash`. Вони потрапляють у git, оновлення - лише через PR. CLI кладе файли в `.agents/skills/`, у `.claude/skills/` робить симлінки на них, а джерело й хеш кожного скіла пише в `skills-lock.json` у корені - у git ідуть усі три. За замовчуванням CLI надсилає анонімну телеметрію для рейтингу на skills.sh; вимикається `DISABLE_TELEMETRY=1`, а `DO_NOT_TRACK=1` вимикає ще й запити на аудит.
- `tdd` вимагає узгодити seams (публічні межі, на яких тестуємо) до написання тестів і виносить рефакторинг за межі циклу red → green - у рев'ю. `grill-me` - заглушка на 157 байт, яка викликає `grilling`: без другого скіла перший неробочий. Єдині виконувані файли серед встановленого - 6 скриптів `heroui-react`, які читають документацію з `mcp-api.heroui.com`, `heroui.com` і `raw.githubusercontent.com`; нічого не записують і запускаються лише на явний виклик.
- Перед встановленням Claude читає `SKILL.md` і скрипти скіла й коротко пояснює, що вони роблять. При оновленні - повторна перевірка аудитів безпеки на skills.sh (Gen Agent Trust Hub, Socket, Snyk).
- **Ставить автор:** скіли встановлює CLI `npx skills add`, тож запускає його автор. Заборони на запис у `.claude/` немає - Claude туди пише, коли це потрібно (наприклад, у `.claude/plans/`).
- Не беремо: скіли для Drizzle і Playwright (є лише неофіційні), окремий скіл Next.js (документація постачається в `node_modules/next/dist/docs` і відповідає встановленій версії), Feature-Sliced Design, Git Commit, Ponytail, agent-browser, find-skills.
