# 6.16 Ліміт у вакансіях, а не в сторінках

**Етап 6 — Автоматизація та Settings** · строго TDD

Привід (20.11.2026, перша справжня компанія автора): kinggroup.io на PeopleForce - 91 відкрита вакансія, по 10 на сторінку, за алфавітом. `PAGES_TO_CHECK = 5` дав лише 50, і потрібні автору вакансії з кінця алфавіту не потрапили в застосунок.

Корінь - ліміт у сторінках, а розмір сторінки в платформ різний: PeopleForce 10, Workday 20, Lever 100. Ті самі 5 сторінок - то 50 вакансій, то 500.

**Рішення автора 20.11.2026:** ліміт - у вакансіях, сторінки рахуються з розміру сторінки платформи; читання, як і зараз, зупиняється, щойно сторінки скінчились. Замінює `PAGES_TO_CHECK` (назва змінної, значення за замовчуванням і межі - на старті задачі). До цієї ж задачі автор долучив ідею з `analyze` «ручні перевірки лише по перших сторінках» (нижче без змін): з більшим лімітом ручний Check now на великій дошці PeopleForce чекатиметься довше, тож вирішити разом.

Перевірити на старті: що життєвий цикл робить з вакансіями, яких не видно через досягнутий ліміт (не мають закриватися), і чи вистачає 10 хвилин тайм-ауту завдання черги на найдовше джерело (`src/server/queue/README.md`).

## Рішення автора 20.11.2026 (на старті задачі)

- **Ліміт - 500 вакансій** за замовчуванням, змінна `VACANCIES_TO_CHECK` замість `PAGES_TO_CHECK`. Сторінки - `ceil(ліміт / розмір сторінки платформи)`: PeopleForce 50, Workday 25, Lever і Hurma 5.
- **Неповне читання нічого не закриває.** Парсер каже, чи дочитав список до кінця; якщо ні (ліміт чи перша сторінка) - життєвий цикл лише додає й оновлює, а зниклими нічого не позначає. Досі ліміт вважався повним списком, і вакансії за ним щоразу зникали й поверталися новими Unread.
- **Глибина читання за видом перевірки:**

  | Перевірка | Читає |
  | --- | --- |
  | Check all вручну | першу сторінку |
  | Автоперевірка | повністю, якщо джерело не читалось повністю понад добу; інакше першу сторінку |
  | Check now компанії, перша перевірка після Save | повністю |
  | Retry невдалих | так само, як перевірка, що збійнула |
  | Пробне читання в Find pages і Find new pages | першу сторінку; більше - «N+ vacancies» |

  Платформи без сторінок (Greenhouse, Ashby тощо) завжди віддають увесь список - для них нічого не міняється.

## Ідея з analyze: ручні перевірки лише по перших сторінках


Рішення автора 19.11.2026 (тоді, ще як `analyze`): поки не робимо. Повернутися, коли база заповниться справжніми компаніями і стане видно, що пошук чи ручна перевірка справді чекаються задовго саме через пагінацію.

## Ідея автора

- **Повна перевірка (усі сторінки до `PAGES_TO_CHECK`) - лише у фоні**, коли користувач її не чекає: автоперевірка за розкладом (етап 6).
- **Перевірка, яку користувач запустив і чекає** (Check all, Check now, перша перевірка після Save, пробне читання у Find pages), - **лише перша сторінка** кожної дошки, без пагінації.

Чому не «лише перша сторінка завжди»: з першої сторінки не видно, що вакансія зникла. Життєвий цикл позначає вакансію закритою, коли її немає в повному списку (`src/server/vacancies/README.md`). До того ж не всі платформи сортують за датою, тож нова вакансія не обовʼязково на першій сторінці. Неповне читання не має закривати вакансії, яких на ній не видно.

## Заміри на справжній мережі (19.11.2026)

| Що | Час |
| --- | --- |
| Сторінка Lever API на 100 вакансій | 2,5-4 с; відповідь ~0,9-1,9 МБ, бо Lever віддає повні описи |
| Пауза ввічливості між запитами до одного хоста | 2 с, сторінки однієї дошки - одна за одною |
| Пробне читання Palantir (307 вакансій, 4 сторінки) | ~10 с |
| Перевірка, що дошки PeopleForce не існує | ~2 с (редирект на `/404`) |
| Пошук на сайті компанії (головна → `/careers` → `/jobs` → sitemap → до 3 сторінок) | до ~10 с, усе на одному хості з паузами |

Після Save перша перевірка читає ті самі дошки, що щойно прочитало пробне читання, - очікування подвоюється.

## Інші варіанти, обговорені тоді ж

1. **Find pages показує знахідки поступово:** адреси одразу, кількість вакансій дочитується в рядку зі спінером.
2. **Пробне читання - лише перша сторінка**, «100+ vacancies» для великих дошок (Palantir ~10 с → ~3 с). Ліміт сторінок уже є (`maxPages`).
3. **Не читати двічі:** результат пробного читання живе на сервері кілька хвилин, і перша перевірка після Save бере вакансії з нього.
4. **Менша пауза для API платформ** (`api.lever.co` - публічний API). Суперечить правилу ввічливості з [`docs/security.md`](https://github.com/Odinokun/job-digger/blob/plan-v1.4.0/docs/security.md); ліміти Lever не перевірені.
5. **Частина сторінок часто, повний список рідше** - нові вакансії швидко, зниклі із затримкою.
6. **Умовні запити** (`ETag` / `If-Modified-Since`, відповідь 304 без тіла, якщо дошка не змінилась). Чи підтримують їх платформи - не перевірено.
