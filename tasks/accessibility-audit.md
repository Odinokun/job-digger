# Перевірка доступності

**Поза етапами — UI** · аудит, потім задачі на виправлення

План автора 24.11.2026, не на зараз. Репозиторій стане публічним: його показуватимуть рекрутерам і на технічних співбесідах. Перед цим застосунок треба перевірити на доступність. Брати перед [public-repo-polish.md](public-repo-polish.md): перекладати й причісувати варто вже виправлений код.

## Що перевірити

- Назви елементів для читача екрана: `aria-label` у кнопок без тексту (частина вже є, `IconButton` у `src/app/components/icon-button.tsx`), підписи полів, назви модалок і вкладок.
- Клавіатура: усе доступне з клавіатури, видимий фокус, порядок Tab, фокус повертається після закриття модалки й drawer.
- Оголошення змін: стан перевірки, сповіщення, оптимістичні дії над рядком (`role="status"`, `aria-live`).
- Контраст тексту й іконок в обох темах. Частину вже звіряли для теми Ink ([src/app/README.md](../src/app/README.md#тема-ink)).
- Структура сторінки: заголовки по порядку, landmarks, `lang` на `<html>` за мовою інтерфейсу.
- `prefers-reduced-motion` для анімацій.
- Масштаб 200% і телефон.

## Що вирішити на старті

- Чим міряти. Lighthouse у Chrome DevTools не потребує нових залежностей. Автоматична перевірка в E2E (наприклад, axe для Playwright) - це нова залежність, вона потребує обґрунтування за правилами проєкту.
- Ручна перевірка з VoiceOver: які сценарії пройти.
- Яка ціль: рівень WCAG (A чи AA) і чи записувати результат у README.
