# 3.09 Парсер Workday

**Етап 3 — Парсинг і вакансії** · строго TDD

Читання вакансій Workday. Увага: Workday віддає список посторінково, тому ця картка — перша, де реально знадобиться пагінація (картка 3.12).

План: [docs/discovery-and-parsing.md](https://github.com/Odinokun/job-digger/blob/plan-v1.4.0/docs/discovery-and-parsing.md) розділ 6.

## Рішення (18.11.2026)

- Публічної документації API немає - парсер ходить у `/wday/cxs/{tenant}/{site}/jobs`, як сам career site. Формат звірено справжніми запитами (NVIDIA, Salesforce, Workday), деталі - `src/server/parsers/README.md`, «Workday».
- Список віддається лише на POST з JSON, тож HTTP-клієнт отримав `post(url, json)`: ті самі SSRF, ліміти, розклад і повтори, але редирект повертається як відповідь.
- Сторінки по 20 (більше Workday не приймає), до 5 сторінок - щонайбільше 100 вакансій з джерела. Кінець - за `total` першої сторінки.
- ID - `externalPath`, бо номер заявки не унікальний. Локація - `locationsText` як є («2 Locations»). Окремий запит на кожну вакансію заради точного ID і локацій - ні: 100 запитів замість 5.
- Невідомий tenant (422) лишається `bad-status`, а не `not-found`.
