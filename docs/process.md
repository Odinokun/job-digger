# Job Digger - Процес розробки

Частина технічного плану Job Digger v1.3.0. Карта всіх файлів - у [README](README.md).

## 14. Процес розробки

### Репозиторій

Один репозиторій з одним Next.js-застосунком, де разом фронтенд (сторінки, компоненти, HeroUI) і бекенд (Server Actions, API-маршрути для обробника розкладу, черга, парсери, модуль запитів, робота з БД). Вони розведені по папках, наприклад `src/app` і `src/server`. Мультипакетний монорепозиторій (Turborepo, pnpm workspaces) не потрібен. Детальна структура папок - наступний крок після плану.

### Мова

- **Українською:** документація (файли в `docs/`, README, описи задач) і коментарі в коді. Згодом їх можуть перекласти англійською.
- **Англійською:** коміти в Git, назви в коді (змінні, функції, файли, таблиці й колонки БД), назви тестів, логи й технічні повідомлення про помилки.
- Тексти інтерфейсу (меню, заголовки, кнопки, підписи, повідомлення) - англійською й українською з першої версії, через ключі у двох файлах перекладів (next-intl). Тест перевіряє, що в обох файлах однакові ключі. За замовчуванням - English. Дані із сайтів (назви вакансій і компаній, локації) не перекладаються.
- Коміти - у форматі Conventional Commits: `feat: add Greenhouse parser`, `fix: ...`, `test: ...`, `docs: ...`.

### Як працюємо: маленькі кроки

- Кожен етап ділиться на маленькі кроки. Один крок - одна невелика зміна (зазвичай «один тест + код, що робить його зеленим») і один коміт.
- **Перед кроком** - коротке пояснення українською: що робимо і навіщо, які файли зміняться, які нові поняття з'являться (з поясненням при першій появі і посиланням на офіційну документацію). Код пишеться лише після «ок» або відповідей на питання.
- **Після кроку** - що змінилося, як перевірити (наприклад, яку команду запустити для тестів) і запропонований англійський текст коміту.
- **Коміт - лише після перегляду автором.** Claude не комітить одразу після кроку: він показує текст коміту і чекає. Автор сам передивляється змінені файли і дає окреме «ок» саме на коміт. «Ок» на крок дозволяє писати код, але не комітити його.
- Темп можна змінити будь-коли («пояснюй коротше», «ці кроки можна об'єднати»).
- Правила цього розділу переносяться у `CLAUDE.md` у корені проєкту, щоб кожна нова сесія Claude Code читала їх автоматично.

### Задачі в Trello

Дошка JobDigger у Trello, доступ для Claude - через конектор Trello.

Колонки: Analyze → Backlog → To Do → In Progress → Testing → Done.

- **Analyze** - ідеї, що з'явилися під час розробки, але ще не продумані й не включені в план. Після обговорення і внесення в план задача переходить у Backlog.
- **Backlog** - усі задачі з плану.
- **To Do** - задачі, взяті в найближчу роботу.
- **In Progress** - задача, над якою працюємо зараз. Лише одна за раз.
- **Testing** - код готовий, автор перевіряє вручну. Тести зелені, якщо задача їх передбачає: інфраструктурні задачі (каркас, службові файли, конфігурація) тестів не мають, і для них критерій - ручна перевірка за описом у PR.
- **Done** - перевірено і погоджено автором.

Одна картка - одна задача (наприклад, «Парсер Greenhouse»). Маленькі кроки задачі - чекліст усередині картки. Кожна картка має мітку етапу («Етап 1» ... «Етап 7»), опис - українською.

Після затвердження плану Claude розбиває етапи на задачі й показує список. Картки створюються лише після «ок». Під час роботи Claude переносить картку в In Progress, відмічає пункти чекліста і переносить у Testing. У Done картка переходить лише після перевірки автором.

### Git: GitHub Flow

- `main` завжди робочий. Напряму в `main` нічого не комітимо.
- Одна гілка - одна картка Trello. Назва гілки - тип і коротка суть англійською: `feat/greenhouse-parser`, `fix/duplicate-detection`.
- Кроки - коміти в гілці: один маленький крок - один коміт у форматі Conventional Commits.
- Коли задача готова і її тести зелені - Pull Request, картка переходить у Testing. Опис PR - українською: що зроблено, посилання на картку і обов'язковий розділ «Як перевірити» з конкретними командами й очікуваним результатом.
- Рев'ю, ручну перевірку і злиття в `main` робить автор. Спосіб злиття - squash merge: коміти гілки стають одним комітом у `main` з назвою PR. Після злиття гілка видаляється, картка переходить у Done.
- GitHub Actions запускає всі тести на кожен PR. PR із червоними тестами не зливається.
- Коміти і PR робить Claude, але лише після того, як автор передивився змінені файли і окремо погодив коміт. Злиття - завжди автор.

Правила:

- Скіли ставляться лише в проєкт (`.claude/skills/`) через `npx skills add`, не через `curl | bash`. Вони потрапляють у git, оновлення - лише через PR.
- Перед встановленням Claude читає `SKILL.md` і скрипти скіла й коротко пояснює, що вони роблять. При оновленні - повторна перевірка аудитів безпеки на skills.sh (Gen Agent Trust Hub, Socket, Snyk).
- Ставить автор: інструменти Claude не можуть писати в `.claude/`.

Не беремо: скіли для Drizzle і Playwright (є лише неофіційні), окремий скіл Next.js (документація постачається в `node_modules/next/dist/docs` і відповідає встановленій версії), Feature-Sliced Design, Git Commit, Ponytail, agent-browser, find-skills.

Після встановлення скілів на етапі 1 - прогін фінального плану через Grill Me в Claude Code. Рішення з «Журналу змін» не переглядаються, шукаємо непокрите: стани помилок в інтерфейсі, порожні екрани, крайні випадки в даних.

### Тести і TDD

- **Логіка - строго за TDD:** спершу тест, який падає, потім код, який робить його зеленим. Це парсери, правила життєвого циклу вакансій, очищення URL і дублікати, захист від SSRF, розрахунок наступної автоперевірки, CSV, черга.
- **Верстка й дрібниці UI** - без строгого TDD.
- **E2E - TDD на рівні етапу:** на початку етапу сценарій пишеться як критерій готовності (червоний), наприкінці етапу він має бути зеленим.

Рівні тестів:

1. **Юніт-тести (Vitest)** - основна маса, швидкі, для чистої логіки.
2. **Інтеграційні тести (Vitest + PostgreSQL у Docker, окрема тестова база)** - черга, умовне видалення з урахуванням Favorites, одночасні зміни.
3. **E2E (Playwright Test)** - 5-7 ключових сценаріїв: додавання компанії, Check now і поява вакансій в Unread, Read/Favorite, Mark all as read з діалогом, видалення компанії, CSV туди й назад.

Правила:

- Тести ніколи не ходять на справжні сайти. Замість них - локальний фейковий сервер зі збереженими відповідями платформ. Для кожного парсера зберігається реальна відповідь платформи у файлі.
- У тестовому режимі захист від SSRF дозволяє лише адресу фейкового сервера.
- Playwright Test - лише інструмент для тестів, у продакшн-код не потрапляє (браузерний парсинг відкладено, [розділ 6](discovery-and-parsing.md)).
