# Job Digger - Пошук джерел, парсинг і життєвий цикл вакансій

Частина технічного плану Job Digger v1.4.0. Карта всіх файлів - у [README](README.md).

## 5. Додавання компанії та пошук кар'єрних сторінок

**Обов'язкова вимога до інтерфейсу:** додавання компанії відбувається через popup/modal **Add company** на сторінці **Companies**, НЕ на окремій сторінці. Увесь сценарій додавання виконується в цьому модальному вікні.

1. **Введення URL у модалі.** Головний сайт, наприклад bosch.com, або готова кар'єрна адреса. Головна адреса зберігається разом зі шляхом: bosch.com/de і bosch.com/ua - різні компанії (наприклад, для різних країн).
2. **Find pages.** Кнопка в модалі запускає визначення компанії та пошук кар'єрних сторінок. Отримуємо назву компанії і головний домен. Назву можна змінити (наприклад, «Bosch UA»).
3. **Пошук джерел** - від найнадійнішого способу до найменш надійного:
   - посилання з сайту компанії на ATS (наприклад, кнопка Jobs веде на Greenhouse);
   - кар'єрні сторінки на самому сайті: посилання Careers / Jobs / Karriere / Вакансії, типові адреси (/careers, /jobs), sitemap;
   - перевірка ATS за назвою компанії (PeopleForce, Greenhouse, Lever, Workday, Ashby тощо). Такі знахідки позначаються «знайдено за назвою - перевір».

   Зовнішній пошуковий API в першій версії не використовується. Якщо джерело не знайдено, кар'єрну адресу можна вставити вручну в тому самому модальному вікні.

4. **Перевірка відповідності.** Не прив'язуємо знайдену сторінку до компанії лише через схожу назву.
5. **Попередній перегляд.** Показуємо знайдені джерела, автоматично заповнені поля та можливість ручного редагування. Кожне знайдене джерело пробно читається ще до показу списку: показуємо платформу, URL і результат (наприклад, «Greenhouse - 34 вакансії» або «Власна сторінка - не підтримується»). Вибрати для відстеження можна лише джерела, які читаються.
6. **Save.** Користувач підтверджує відредаговані поля та вибрані джерела кнопкою Save у модалі. Зберігаємо головну адресу компанії (зі шляхом) та вибрані кар'єрні адреси.
7. **Перша перевірка.** Якщо є кар'єрні джерела, одразу запускаємо перевірку цієї компанії. Якщо придатних джерел немає або жодне не вибрано - компанія потрапляє в Not tracked з відповідним статусом.

**Дублікати.** Правила порівняння адрес компанії - у [`src/lib/companies`](../src/lib/companies/README.md), пошук конфлікту - у [`src/server/companies`](../src/server/companies/README.md); тексти повідомлень і їх показ - у модалці Add company. Якщо знайдене джерело вже відстежується в іншій компанії, у списку знахідок біля нього показується «вже відстежується в ...». Рішення - за користувачем.

Пошук джерел виконується при додаванні будь-якого типу URL, навіть якщо користувач уже надав готову кар'єрну сторінку.

У регулярних перевірках вакансій не потрібно щоразу повторювати глобальний пошук кар'єрних сторінок.

## 6. Парсинг вакансій

Використовуємо послідовність стратегій:

1. Офіційний або публічний API платформи (ATS), якщо доступний.
2. Структуровані дані сторінки (schema.org JobPosting), отримані HTML-парсингом.

Джерело вважається таким, що читається, якщо спрацювала одна з цих стратегій. Власні сторінки компаній без стандартної розмітки в першій версії не підтримуються (статус Unsupported). Можливі розширення пізніше: універсальний пошук посилань на вакансії, ручне налаштування для сайту, витягування вакансій за допомогою ШІ.

Браузерний парсинг через Playwright у першій версії не використовується. Його додамо, лише якщо трапиться важливий сайт, якому він справді потрібен.

Підтримуємо пагінацію API платформ, а також нумеровану пагінацію та Next на сторінках, наскільки це технічно можливо. Load more і динамічне підвантаження потребують браузера, тому відкладаються разом із Playwright.

Налаштування:

| Параметр               | Значення             |
| ---------------------- | -------------------- |
| Pages to check         | 5                    |
| Parallel source checks | 5                    |
| Parallelism range      | 1-10                 |
| Retry attempts         | До 2 повторних спроб |

Ці параметри спільні для всіх користувачів і задаються через ENV.

Перевіряються лише перші N сторінок (Pages to check). Досягнення ліміту - нормальне завершення, перевірка вважається успішною. Більшість ATS віддає весь список одним запитом, тому ліміт стосується лише джерел із посторінковою видачею.

Відомий ризик: якщо сайт сортує вакансії не за датою, вакансія може випасти за межі перших сторінок, бути видаленою, а пізніше повернутися як нова Unread. Більшість сайтів сортує від нових до старих, тому ризик прийнятний.

Якщо перевірка джерела завершилася помилкою (сайт не відповів, збій мережі, тайм-аут), **не видаляємо його раніше збережені вакансії**.

Саме тому джерело веде лічильник послідовних збоїв і час останньої успішної перевірки: після помилки нічого не видаляється, і без цих полів неможливо відрізнити живі вакансії від тих, що залишилися від джерела, яке не відповідає вже місяць. З відстеження джерело автоматично не знімається, показ - у [розділі 4.2](ui.md).

Нуль знайдених вакансій - успішний результат лише тоді, коли парсер достовірно встановив, що вакансій справді немає. Порожній список від API платформи - достовірний результат, тож усі вакансії джерела видаляються (крім вакансій із Favorites - вони отримують позначку Closed). Нуль зі сторінки (schema.org JobPosting) вважається збоєм, бо, найімовірніше, змінилася верстка. Вакансії в такому разі не видаляються.

Довіряємо лише цілим відповідям. Вакансія без назви або без адреси, що починається з `http` чи `https`, не зберігається - у списку з неї нічого не показати й нікуди відкрити. Кількість відкинутих записів лишається в деталях завдання як parse warning: це сигнал, що парсер треба правити, а не що на сайті немає вакансій.

Відповідь, обрізана лімітом розміру ([розділ 13](security.md)), - це збій джерела, а не частковий результат. Інакше обрізаний список виглядав би як «частина вакансій зникла» і потягнув би за собою їхнє видалення. Вакансії такого джерела лишаються недоторканими, як і після будь-якої іншої помилки.

Ввічливість до сайтів:

- до одного сайту - не більше 2 запитів одночасно і пауза 2 секунди між запитами;
- тайм-аут 20 секунд на запит;
- чесний User-Agent із назвою застосунку;
- відповідь 429 (забагато запитів) - чекаємо стільки, скільки просить сайт (Retry-After);
- повторні спроби (до 2) - лише при збоях мережі й помилках сервера, з паузою, що зростає. На «сторінку не знайдено» повторів немає.

Запити до різних сайтів ідуть паралельно, тому пауза сповільнює лише джерела на тому самому сайті.

## 7. Життєвий цикл вакансії

Кожна вакансія має такі дані: title, URL, location, first detected, last checked, статус Unread/Read, Favorite, позначка Closed. Title і URL обов'язкові - без них вакансія не зберігається (розділ 6); location необов'язкова, і в списку тоді стоїть «—» ([розділ 4.1](ui.md)). Компанія і source URL беруться через зв'язок «вакансія → джерело → компанія» і окремо не зберігаються. Description, salary та employment type не зберігаються.

Внутрішній ключ вакансії: джерело + ID вакансії на платформі. Якщо ID немає - джерело + очищена URL (без міток відстеження на кшталт `utm_*` і `gh_src`, без слеша в кінці).

| Подія                                    | Дія                                                                                                |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Вакансія з'явилася вперше                | Створити як Unread                                                                                 |
| Вакансія знайдена повторно               | Оновити last checked, зберегти Read/Favorite                                                       |
| Змінилася назва                          | Оновити назву, зберегти Read/Favorite                                                              |
| Змінилася URL                            | Якщо є ID платформи - оновити URL. Якщо ID немає - старий запис видалити, новий створити як Unread |
| Вакансія зникла після успішної перевірки | Видалити з БД. Якщо вона у Favorites - залишити з позначкою Closed                                 |
| Раніше зникла вакансія повернулася       | Показати як нову Unread                                                                            |
| Перевірка завершилася помилкою           | Не видаляти вакансії цього джерела                                                                 |

Правило «з'явилася вперше - Unread» діє і для першої перевірки нової компанії: усі її поточні вакансії потрапляють в Unread.

Вакансія з позначкою Closed видаляється, коли користувач прибирає її з Favorites.

**Одночасні зміни.** Користувач може працювати з вакансіями під час перевірки:

1. Кожна сторона змінює лише свої поля. Перевірка ніколи не змінює Read/Favorite, дії користувача ніколи не змінюють назву чи URL. Оновлюються лише потрібні колонки, а не весь запис.
2. Видалення зниклих вакансій виконується однією командою з умовою: звичайні видаляються, вакансії з Favorites отримують позначку Closed. Вакансія, щойно додана у Favorites, не загубиться.
3. Mark all as read діє лише на вакансії, що були в списку на момент підтвердження: межа - дата виявлення на час натискання, а не перелік рядків, які встигли завантажитися в інтерфейсі ([розділ 4.1](ui.md)). Знайдені пізніше лишаються Unread. Якщо вакансія зникла в момент дії, дія над нею нічого не робить, без помилки.

Між різними джерелами дублікати не об'єднуємо. Усередині одного джерела повторні записи не створюємо.
