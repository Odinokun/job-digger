# Job Digger - База даних

Частина технічного плану Job Digger v1.4.0. Карта всіх файлів - у [README](README.md).

## 9. База даних

Таблиці, які вже є в коді (`users`, `companies`, `career_sources`), описані схемою
Drizzle, а рішення щодо них - у [README бази](../src/server/db/README.md).

Пропонована логічна модель:

| Таблиця        | Призначення                                                                          |
| -------------- | ------------------------------------------------------------------------------------ |
| users          | Власник даних, майбутня багатокористувацька підтримка                                |
| companies      | Назва, головна URL (разом зі шляхом), статус                                         |
| career_sources | Кар'єрні URL, платформа, статус, зв'язок із компанією, стан перевірок                |
| vacancies      | Вакансії: ключ, title, URL, location, дати, Read/Favorite, позначка Closed           |
| check_runs     | Агрегована історія перевірок і позначка показаного підсумку                          |
| check_tasks    | Завдання (одне на кар'єрне джерело), пріоритет, спроби, статуси, помилки, блокування |
| settings       | Налаштування користувача                                                             |

Зв'язки:

- Один User має багато Companies.
- Одна Company має багато Career Sources.
- Одне Career Source має багато Vacancies.
- Один Check Run має багато Check Tasks.
- Одне Career Source має багато Check Tasks.

Частина колонок існує лише для станів, які інтерфейс мусить показувати:

- `check_runs` - позначка, що підсумок уже показано. Перевірка часто завершується, коли вкладка закрита, а підсумок має спливти один раз при поверненні ([розділ 8](checks-and-queue.md)).
- `check_tasks` - пріоритет: ручні дії користувача беруться з черги раніше за фонові. Серед статусів є скасоване завдання - для випадку, коли компанію видалили посеред її перевірки ([розділ 8](checks-and-queue.md)).

Для першої локальної версії використовуємо одного системного користувача. Онлайн-доступ у майбутньому буде ізольований за користувачами.

Дані кожного користувача окремі: компанії, джерела, вакансії зі статусами Read/Favorite, налаштування. Якщо двоє користувачів стежать за однією компанією, її перевіряють окремо для кожного, для кількох користувачів це прийнятно.

Авторизація: локально її немає. Онлайн - лише вхід через Google, без логіна й пароля. Після входу email порівнюється зі списком дозволених email у змінних середовища (ENV), у коді список не зберігається.

Технічні записи check_tasks можуть зберігати деталі помилок, але **History UI** відображатиме тільки погоджені п'ять агрегованих полів.

Завдання Check now, Retry і пошуку сторінок теж записуються в check_tasks, але не прив'язуються до рядка History (check_runs).
