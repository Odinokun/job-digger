# src/server/companies - компанії

Правила, що стосуються адрес компаній: очищення адреси перед порівнянням і пошук
конфлікту з уже доданими компаніями. Таблиці й рішення щодо них -
[`db`](../db/README.md), сценарій додавання компанії -
[розділ 5](../../../docs/discovery-and-parsing.md).

## Файли

| Файл            | Що в ньому                                                       |
| --------------- | ---------------------------------------------------------------- |
| `url.ts`        | `normalizeCompanyUrl` - адреса в порівнянній формі, `companyUrlHost` - її хост |
| `duplicates.ts` | `findCompanyUrlConflict` - що вже є серед компаній користувача    |
| `list.ts`       | `listCompanies` і `countCompaniesByTab` - списки для сторінки     |
| `platform.ts`   | `detectPlatform` - платформа джерела, виведена з його адреси       |
| `add.ts`        | `addCompany` - додавання компанії з однією карʼєрною сторінкою      |
| `suggest.ts`    | `suggestCompanyFields` - підказки для полів модалки з однієї адреси |

## Що робить очищення адреси

| Вхід                        | Результат              | Чому так                                                      |
| --------------------------- | ---------------------- | ------------------------------------------------------------- |
| `HTTPS://WWW.Bosch.com/`    | `bosch.com`            | протокол, `www.` і слеш у кінці іншої компанії не роблять      |
| `bosch.com/DE/`             | `bosch.com/DE`         | шлях лишається, разом із регістром                            |
| `bosch.com/de?lang=de#top`  | `bosch.com/de?lang=de` | fragment до сервера не доходить, query - іноді єдина різниця   |
| `   ` (порожнє)             | відмова `empty`        | -                                                             |
| `не адреса`                 | відмова `not-a-url`    | -                                                             |
| `ftp://bosch.com`           | відмова `unsupported-scheme` | завантажуємо лише http і https                          |

Шлях зберігається, бо `bosch.com/de` і `bosch.com/ua` - різні компанії, наприклад
національні версії. Регістр шляху теж зберігається: у HTTP шлях регістрозалежний, і
план вимагає нехтувати регістром лише в домені. Наслідок, про який варто знати:
`bosch.com/DE` і `bosch.com/de` додадуться як дві компанії.

## Рішення

**Результат-обʼєкт, а не виняток.** Крива адреса - очікуваний ввід користувача, а не
виняткова ситуація: форма додавання мусить показати помилку поля, і тип
`{ ok: false; reason }` змушує цей випадок обробити.

**Розбір через `URL`, а не регулярками.** Стандартний парсер сам приводить хост до
нижнього регістру, знімає стандартний порт і переводить національні домени в punycode.
Якщо протоколу немає, підставляється `https://` - інакше `new URL` не розбере рядок.

**Два види конфлікту.** `exact` блокує додавання, `same-domain` - лише попереджає: на
одному домені може жити кілька різних компаній.

**Домен обчислюється в SQL через `split_part`**, а не шукається як `like 'bosch.com%'`:
інакше `bosch.com.ua` вважався б тим самим доменом, що `bosch.com`. Повний перегляд
кількасот рядків дешевший за окрему колонку з доменом; якщо список компаній виросте
настільки, що це стане помітним, додамо колонку з індексом тоді.

**Порядок компаній у попередженні задає код** (`order by name`), а не база. Без явного
порядку PostgreSQL віддає рядки як йому зручно: тест на порядок якийсь час проходив
випадково, і впав лише тоді, коли порядок перевірили мутацією.

## Списки для сторінки Companies

**Вкладка - це запит, а не колонка.** Tracked означає «є хоч одне джерело з
`is_tracked`», Not tracked - «немає жодного», тож компанія, чия єдина сторінка
не підтримується, лишається в Not tracked, а її адреса зберігається.

**Джерела тягнемо другим запитом** за `in (...)`, а не join-ом: join повторював би
рядок компанії на кожне джерело, а `json_agg` ускладнив би запит заради того самого
результату на півсотні рядків.

**Обидва лічильники рахуються одним запитом**, бо обидва числа стоять у назвах
вкладок одночасно.

**Порядок задає код** (`order by name`), а не база. Без явного порядку тест на
сортування проходив випадково - і впав лише після того, як порядок перевірили
мутацією.

**Ліміт за замовчуванням - 50**; Load more і keyset-пагінація приходять із
задачею 2.10.

## Платформа джерела за адресою

Поки автоматичного пошуку немає (етап 5), платформа виводиться з адреси, яку ввів
користувач: інакше жодне додане руками джерело не можна було б відстежувати, і
вкладка Tracked лишалася б недосяжною.

**Порівнюється межа лейбла домену**, а не кінець рядка: `host === suffix ||
host.endsWith("." + suffix)`. Із простим `endsWith` будь-хто міг би назвати домен
`not-greenhouse.io` і ми прийняли б його за дошку Greenhouse.

**У переліку лише хости самої платформи.** Кастомний домен клієнта ATS
(`jobs.company.com`) дає `unsupported` - адреса про нього нічого не каже. Так само
`schema_org` не повертається ніколи: розмітку JobPosting видно лише з вмісту
сторінки, тому справжнє підтвердження дасть пробне читання в етапі 3.

| Суфікс хоста                            | Платформа   |
| --------------------------------------- | ----------- |
| `greenhouse.io`                         | greenhouse  |
| `lever.co`                              | lever       |
| `ashbyhq.com`                           | ashby       |
| `myworkdayjobs.com`, `myworkdaysite.com` | workday    |
| `peopleforce.io`                        | peopleforce |
| решта                                   | unsupported |

Звідки взяті домени - у коментарі до `PLATFORM_DOMAINS`: у Greenhouse офіційно
описаний лише `boards.greenhouse.io`, решта хостів перевірена запитами.

## Додавання компанії

`addCompany` - уся серверна частина модалки Add company. Автоматичного пошуку
сторінок у ній немає: він приходить в етапі 5, тому платформа джерела виводиться
з адреси, а `discovery_status` лишається `not_checked` - пошуку ще не було, і це
не те саме, що «не знайдено».

**Відмова - результат, а не виняток.** Кожен випадок (`name-required`,
`company-url`, `career-url`, `already-added`, `same-domain`) модалка мусить
показати, тому вони лежать у типі `AddCompanyResult` і їх не можна проґавити.
Тексти повідомлень живуть у перекладах, а не тут.

**`same-domain` - попередження, а не помилка.** Перший Save повертає список
компаній того самого домену, повторний із `sameDomainConfirmed` зберігає.
Точний збіг (`already-added`) не проходить і з підтвердженням.

**Уся перевірка вводу - до першої вставки**, а компанія з її джерелом пишуться в
одній транзакції: інакше крива карʼєрна адреса лишила б у базі компанію без
джерела.

**Адреса зберігається в абсолютній формі** (`absoluteCompanyUrl`): без протоколу
`<a href>` у списку компаній став би відносним посиланням. Порівнянна форма
лежить окремо, у `normalized_url`.

**Останнє слово за unique-індексом, а не за перевіркою.**
`findCompanyUrlConflict` виконується до вставки й дає дружній текст, але
атомарним він бути не може: між перевіркою і вставкою інший запит може додати ту
саму компанію. Тому вставка йде з `on conflict (user_id, normalized_url) do
nothing`, і якщо вона нічого не повернула - компанію перечитуємо й віддаємо той
самий `already-added`. Результат не залежить від того, хто виграв гонку, тож
застосунок витримує кількох користувачів і кілька вкладок одного користувача.

Це покрито тестом із двома зʼєднаннями: сусіднє тримає незакомічену вставку,
`addCompany` стає в чергу за блокуванням індексу, і аж після `commit` отримує
`already-added`. Момент блокування тест вичікує опитуванням `pg_stat_activity`,
а не таймером - інакше він проходив би через дружню перевірку й про гонку не
казав би нічого. Опитування йде поза транзакцією: усередині неї статистика
віддається з кешованого знімка, у якому сусіднього зʼєднання ще немає.

## Межі

`findCompanyUrlConflict` приймає **уже очищену** адресу: очищення й пошук - два
окремих кроки, бо очищену форму все одно треба зберегти в `companies.normalized_url`.

Тексти повідомлень («Компанія вже додана», «На цьому домені вже є: ...») і їх показ -
задача модалки Add company, не цих модулів.

## Підказки для полів Add company

`suggestCompanyFields` розбирає одну вставлену адресу й віддає, що підставити в поля
модалки. Запитів у мережу немає: усе видно з рядка.

| Вставлено                  | Головний сайт | Назва  | Карʼєрна сторінка          |
| -------------------------- | ------------- | ------ | -------------------------- |
| `bosch.com`                | `bosch.com`   | Bosch  | -                          |
| `bosch.com/de/careers/jobs`| `bosch.com`   | Bosch  | `bosch.com/de/careers/jobs`|
| `about.gitlab.com`         | `about.gitlab.com` | Gitlab | -                     |

**Назва - передостанній лейбл домену**, з кроком назад на домені другого рівня
(`bosch.com.ua` - Bosch, інакше вийшла б «Com»). Список таких суфіксів короткий і
живе в коді: повний Public Suffix List оновлюється окремо від нас, а виграш від нього
тут - кілька рідких доменів. Абревіатури не розпізнаються: `bbc.co.uk` дасть «Bbc».

**Усе, що після домену, їде в поле карʼєрної сторінки.** Головний сайт обрізається до
домену, і без цього вставлений шлях просто зникав би. Наслідок: `bosch.com/de` теж
потрапить у карʼєрне поле, хоча це національна версія сайту - поля редаговані, і
користувач переносить адресу сам. Правило свідомо не вгадує за словами в шляху
(`careers`, `jobs`): такий список довелося б тримати й доповнювати, а вигоди - лише
на крайніх випадках.
