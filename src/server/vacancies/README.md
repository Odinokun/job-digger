# src/server/vacancies - вакансії

Що сервер робить із вакансіями після того, як парсер їх прочитав: ключ і життєвий
цикл. Дані вакансії й дії користувача над нею - docs/discovery-and-parsing.md,
розділ 7.

## Очищена адреса

`cleanVacancyUrl` дає форму, у якій дві адреси однієї вакансії збігаються:

- **без міток відстеження** - `utm_*` і `gh_src` (з плану), `gh_jid` (дублює ID зі
  шляху Greenhouse, знайдено в 3.06), `fbclid` і `gclid` (рекламні мітки Facebook і
  Google). Решта параметрів лишається: `?id=42` розрізняє вакансії;
- **без якоря** (`#apply`) і **без слеша в кінці шляху**;
- **хост у нижньому регістрі**, а регістр шляху - як був: на багатьох сайтах він
  важить;
- **параметри в одному порядку** - `?b=2&a=1` і `?a=1&b=2` однакові.

## Ключ

`vacancyKey` - `id:<ID на платформі>`, а без ID (`null` чи порожній рядок) -
`url:<очищена адреса>`. Ключ унікальний у межах джерела - це тримає індекс
`(source_id, key)` у базі ([`db`](../db/README.md)).

- **З ID адреса на ключ не впливає.** Вона може змінитися, а вакансія лишиться тією
  самою - життєвий цикл (3.13) тоді лише оновить адресу.
- **Без ID зміна адреси - це нова вакансія:** інший ключ, тож старий запис зникне, а
  новий зʼявиться як Unread (див. [Життєвий цикл](#життєвий-цикл)).
- Функція приймає лише `{ externalId, url }`, а не тип парсера: у парсера schema.org
  (3.11) ID може не бути.

## Життєвий цикл

`syncSourceVacancies(db, { sourceId, result, checkedAt })` застосовує одну відповідь
парсера до вакансій одного джерела. `checkedAt` передає той, хто запускає перевірку
(черга, 3.14), а не годинник усередині функції.

| Подія                                         | Дія                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| Вакансія зʼявилася вперше                     | Створити як Unread, дата виявлення = `checkedAt`                        |
| Знайдена повторно                             | Оновити `last_seen_at`, Read і Favorite не чіпати                       |
| Змінилися назва, локація чи адреса (з ID)     | Оновити їх, Read і Favorite не чіпати                                   |
| Змінилася адреса, ID немає                    | Це інший ключ: старий запис зникає, новий створюється як Unread         |
| Зникла після успішної перевірки               | Видалити; з Favorites - лишити з `closed_at = checkedAt`                |
| Успішна перевірка без жодної вакансії         | Те саме для всіх вакансій джерела                                      |
| Неповний список (`truncated`: ліміт чи перша сторінка) | Лише створити й оновити; зниклими нічого не позначати (задача 6.16) |
| Видалена вакансія повернулася                 | Створюється заново як нова Unread                                      |
| Closed-вакансія з Favorites повернулася       | Зняти Closed; Read, Favorite і дата виявлення лишаються                 |
| Перевірка з помилкою (`ok: false`)            | Нічого не змінювати                                                    |
| Той самий ключ двічі в одній відповіді        | Береться перший                                                        |
| Нова вакансія з тією самою назвою, що активна в іншому джерелі компанії | Створити прочитаною і не рахувати новою - див. [Дублікати між джерелами](#дублікати-між-джерелами) |
| Джерело видалили, поки сайт відповідав        | Нічого не писати; видалення, що почалося паралельно, чекає на транзакцію (`FOR KEY SHARE`) і забирає й нові вакансії |

Правило «зʼявилася вперше - Unread» діє і для першої перевірки нової компанії: усі
її поточні вакансії потрапляють в Unread.

### Як це влаштовано

Усе в одній транзакції. Спершу - блокування рядка компанії (див. «Дублікати між
джерелами»), далі три кроки:

1. **Upsert знайдених:** `INSERT ... ON CONFLICT (source_id, key) DO UPDATE`. Оновлює
   лише поля перевірки - `title`, `url`, `location`, `last_seen_at`, `closed_at`.
   Read і Favorite - поля користувача, upsert їх ніколи не пише. Дублікати ключа
   прибираються заздалегідь: PostgreSQL не дає одній команді двічі змінити рядок
   (cardinality violation,
   [документація](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT)).
2. **Зниклі** - рядки джерела з `last_seen_at < checkedAt`, тобто ті, яких upsert не
   торкнувся. Одна команда з CTE: `delete` для звичайних, `update closed_at` для
   Favorites. Список ключів не передається - достатньо дати.
3. **Дублікати між джерелами** - щойно створені вакансії, чия назва є серед
   активних вакансій інших джерел компанії, стають прочитаними. Це єдине місце, де
   перевірка пише Read, і лише в щойно виявлені вакансії (або в сайтову, що
   поступилася платформі) - вакансію, яку людина вже бачила, перевірка не чіпає.

Функція повертає `{ newVacancies, removedVacancies }` - числа рядка History, які
черга додає до запуску (`queue/finish.ts`). Нова - рядок, у якого після upsert
`first_detected_at` дорівнює `checkedAt` і який не став прочитаним дублікатом: оновлення наявної вакансії дату виявлення не
чіпає, а вакансія, що повернулася після видалення, створюється заново і теж нова.
Видалені - усі, що зникли з сайту: і стерті, і Favorites, які щойно отримали Closed.
Favorite, закритий раніше, вдруге не рахується - умова `closed_at is null`. Невдала
перевірка або видалене джерело - нулі.

### Дублікати між джерелами

Задача 6.20, рішення автора 20.11.2026. У компанії буває кілька джерел з тими самими
вакансіями - ATS, агрегатор і власний сайт. Без правила кожна вакансія потрапляла б
в Unread по разу на джерело.

- **Дублікат** - нова вакансія, чия назва збігається з назвою активної (не Closed)
  вакансії **іншого** джерела **тієї самої** компанії. Порівняння - у нижньому
  регістрі, з обрізаними пробілами на краях і стиснутими всередині
  (`comparableTitle` у `lifecycle.ts`). Нечіткого порівняння немає: «PHP developer
  (Payment team)» і «PHP Developer» - різні вакансії. Дві вакансії одного джерела з
  однією назвою (різні міста) - не дублікати.
- **Дублікат не відкидається, а записується прочитаним:** його немає в Unread,
  лічильнику біля Jobs і «N new vacancies», але є в Read і All, і в History він не
  рахується новим. Фільтра назв немає свідомо - автор хоче бачити всі вакансії.
- **Хто стає прочитаним** - `resolveDuplicates`: пізніший. Виняток - **перевага
  платформи над сайтом** (ATS і агрегатори «гнучкіші й живіші»): нова вакансія з
  платформи, чиї дублікати лише сайтові й хоч один непрочитаний, лишається
  непрочитаною, а непрочитані сайтові стають прочитаними. Сайт - платформи з
  `SITE_PLATFORMS` у `duplicates.ts` (schema.org, згодом сторінка за рецептом, 6.21).
- **Паралельні джерела.** Джерела однієї компанії перевіряються одночасно, і без
  черги обидва записали б свою копію непрочитаною. Транзакція блокує рядок компанії
  `FOR NO KEY UPDATE`: він конфліктує сам із собою, тож записи вакансій компанії йдуть
  по черзі, а з `FOR KEY SHARE`, яким вставка джерела перевіряє зовнішній ключ, - ні
  ([документація](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)).
  Перейменування компанії чекає на запис - це мілісекунди.
- Вже записані вакансії правило не переписує: воно діє з першої перевірки після
  6.20.

### Одночасні зміни

Користувач може поставити Favorite саме тоді, коли перевірка видаляє вакансію.
Умова `not is_favorite` перевіряється в момент видалення, а не читається
заздалегідь: PostgreSQL чекає на транзакцію користувача і перевіряє умову ще раз на
оновленому рядку
([Read Committed](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)),
тож вакансія лишається. Позначку Closed вона в цю перевірку не отримає - обидві
частини CTE бачать один знімок бази
([документація](https://www.postgresql.org/docs/current/queries-with.html#QUERIES-WITH-MODIFYING)),
- її поставить наступна.

Тест на це відтворює гонку на двох зʼєднаннях і чекає, поки `pg_stat_activity`
покаже запит, що стоїть на блокуванні. Варіант «прочитати id, тоді видалити за id»
цей тест ловить: вакансія губиться.

Якщо `checkedAt` нової перевірки раптом раніший за попередній (розбіжність
годинників), рядки попередньої мають `last_seen_at > checkedAt` і просто не
видаляються - помилка в безпечний бік. Дві перевірки одного джерела одночасно за
планом не йдуть: одне джерело - одне завдання черги
([docs/checks-and-queue.md](../../../docs/checks-and-queue.md)).

**Remove from Favorites для закритої вакансії** (`setVacancyFavorite`) - теж
рішення за поточним станом рядка, а не за тим, що клієнт бачив у списку: у
транзакції спершу `delete ... where closed_at is not null`, потім `update
is_favorite`. Якщо перевірка саме зняла Closed, бо вакансія повернулася на сайт,
`delete` дочекається її і перевірить умову на оновленому рядку - вакансія лишиться,
лише без Favorite. Якщо навпаки користувач видалив рядок першим, upsert перевірки
після нього не знайде конфлікту й створить вакансію заново як Unread - так само,
як для будь-якої видаленої вакансії, що повернулася.

**Mark all as read** (`countUnread` + `markAllRead`) має межу за `created_at` -
моментом запису рядка за годинником бази, а не за датою виявлення.
`first_detected_at` - це `checkedAt`, момент **старту** перевірки, тож перевірка, що
йде, поки відкритий діалог, вставила б нові вакансії «заднім числом», і межа за
датою виявлення мовчки зробила б їх прочитаними. `countUnread` повертає кількість і
`now()` бази з мікросекундами (`dbTimeText`); `markAllRead` одним `UPDATE` позначає
непрочитані з `created_at` не пізніше цієї межі. Записані пізніше лишаються Unread.

Залишкова гонитва - мілісекунди: рядок, вставлений у транзакції, що почалася до
межі, а закінчилася після, має `created_at` раніший за межу, але в підрахунок не
потрапив, - і буде позначений. Вікно - одна коротка транзакція запису джерела, а не
вся перевірка. Прийнятно (рішення автора 18.11.2026, задача 3.17). Відхилений
варіант - знімок ID через браузер: точний, але обʼєм ріс разом із кількістю
непрочитаних (десятки тисяч ID порціями під ліміт 1 МБ Server Action), і дія не була
атомарною.

**Mark all as unread** (`countRead` + `markAllUnread`, задача 6.18) межі не має
(рішення автора 20.11.2026): у вкладку Read потрапляє лише те, що людина прочитала
сама, перевірка туди нічого не додає. Вакансія, прочитана в іншій вкладці браузера,
поки відкритий діалог, теж повернеться в Unread - саме цього людина й хотіла.

## Списки Jobs

`listVacancies(db, { userId, tab, limit, after })` - порція однієї вкладки
(docs/ui.md, розділ 4.1), від найновішої дати виявлення, при однаковій даті - за
`id`. Користувач визначається через компанію: у вакансії власного `user_id` немає.

| Вкладка     | Умова                                    |
| ----------- | ---------------------------------------- |
| `unread`    | `closed_at is null` і не прочитана       |
| `read`      | `closed_at is null` і прочитана          |
| `favorites` | `is_favorite`, зокрема Closed            |
| `all`       | `closed_at is null`                      |

**Курсор** - той самий, що в списку компаній ([`lib/pagination`](../../lib/README.md#курсор-пагінації)),
але ключ - дата виявлення **текстом із бази**, ISO з мікросекундами (`to_char`).
PostgreSQL зберігає час до мікросекунд, а JS `Date` - лише до мілісекунд: курсор,
зібраний з `Date`, губив би рядки на межі порції. Ключ іншої форми - непридатний
курсор, список починається спочатку.

`hasAnyVacancy(db, userId)` вирішує, який текст показати на порожній вкладці:
«вакансій ще немає» чи текст самої вкладки.

## Позначки користувача

`marks.ts` змінює лише поля користувача - `is_read` і `is_favorite`; назву, адресу
й дати пише тільки перевірка. Вакансія шукається через компанію користувача, тож
id з клієнта не дає змінити чужу. Криве id (не UUID) - `null`, а не помилка бази.

- `setVacancyRead` і `setVacancyFavorite` повертають оновлений рядок списку Jobs
  (`findVacancy`, ті самі поля, що в `listVacancies` - `VACANCY_ROW`), або `null`,
  якщо вакансії вже немає: дія над зниклою нічого не робить, без помилки.
- Remove from Favorites для закритої вакансії її видаляє - див. «Одночасні зміни».
- `countUnread` - кількість вакансій вкладки Unread (та сама умова, що в
  `listVacancies`, - `tabCondition`) і межа - час бази; `markAllRead` - позначає
  прочитаними непрочитані, записані не пізніше межі, і повертає, скільки позначено.
  Разом - Mark all as read, див. «Одночасні зміни».
- `countRead` і `markAllUnread` - те саме для вкладки Read, без межі: Mark all as
  unread (задача 6.18).
- `setCompanyVacanciesRead` - Mark all as read / unread для компанії: `is_read` усіх
  активних (не Closed) вакансій її джерел одним `UPDATE`. Межі, як у загальній дії,
  тут немає свідомо: діалогу й числа немає, дію легко скасувати протилежною, а
  гонитва можлива, лише якщо саме цю компанію в цей момент перевіряють.
