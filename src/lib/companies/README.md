# src/lib/companies - адреси компаній

Чисті функції, що працюють із самим рядком адреси: очищення перед порівнянням,
платформа за хостом, підказки для полів модалки Add company. Жодного запиту в мережу
й жодного звернення до бази - тому ці модулі імпортуються і сервером, і клієнтськими
компонентами.

Серверна частина компаній (дублікати в базі, списки, додавання) -
[`server/companies`](../../server/companies/README.md), сценарій додавання компанії -
[розділ 5 плану](../../../docs/discovery-and-parsing.md).

## Файли

| Файл          | Що в ньому                                                                     |
| ------------- | ------------------------------------------------------------------------------ |
| `url.ts`      | `normalizeCompanyUrl` - адреса в порівнянній формі, `companyUrlHost` - її хост  |
| `platform.ts` | `CAREER_PLATFORMS`, `detectPlatform` і `platformHostSuffix`                     |
| `suggest.ts`  | `suggestCompanyFields` - підказки для полів модалки з однієї адреси             |

## Чому це не в `src/server`

Модалка Add company - клієнтський компонент, а підказки їй потрібні одразу, на
виході з поля адреси: ганяти заради розбору рядка запит на сервер нема за що. Правило
проєкту «модулі з `src/server` не імпортуються в клієнтські компоненти» лишається
цілим, бо тут не серверний код, а спільний.

Межа тримається не словами, а залежностями: у цій теці немає нічого з `drizzle-orm`,
`src/server` чи Node API. Перелік платформ теж живе тут, і `pgEnum("career_platform")`
у схемі будується з нього - інакше клієнт тягнув би схему разом із Drizzle, а
значення в базі й у коді могли б розійтися.

## Що робить очищення адреси

| Вхід                        | Результат              | Чому так                                                      |
| --------------------------- | ---------------------- | ------------------------------------------------------------- |
| `HTTPS://WWW.Bosch.com/`    | `bosch.com`            | протокол, `www.` і слеш у кінці іншої компанії не роблять      |
| `bosch.com/DE/`             | `bosch.com/DE`         | шлях лишається, разом із регістром                            |
| `bosch.com/de?lang=de#top`  | `bosch.com/de?lang=de` | fragment до сервера не доходить, query - іноді єдина різниця   |
| `   ` (порожнє)             | відмова `empty`        | -                                                             |
| `не адреса`                 | відмова `not-a-url`    | -                                                             |
| `ftp://bosch.com`           | відмова `unsupported-scheme` | завантажуємо лише http і https                          |

Шлях зберігається, бо `bosch.com/de` і `bosch.com/ua` - різні компанії, наприклад
національні версії. Регістр шляху теж зберігається: у HTTP шлях регістрозалежний, і
план вимагає нехтувати регістром лише в домені. Наслідок, про який варто знати:
`bosch.com/DE` і `bosch.com/de` додадуться як дві компанії.

**Результат-обʼєкт, а не виняток.** Крива адреса - очікуваний ввід користувача, а не
виняткова ситуація: форма додавання мусить показати помилку поля, і тип
`{ ok: false; reason }` змушує цей випадок обробити.

**Розбір через `URL`, а не регулярками.** Стандартний парсер сам приводить хост до
нижнього регістру, знімає стандартний порт і переводить національні домени в punycode.
Якщо протоколу немає, підставляється `https://` - інакше `new URL` не розбере рядок.

## Платформа джерела за адресою

Поки автоматичного пошуку немає (етап 5), платформа виводиться з адреси, яку ввів
користувач: інакше жодне додане руками джерело не можна було б відстежувати, і
вкладка Tracked лишалася б недосяжною.

**Порівнюється межа лейбла домену**, а не кінець рядка: `host === suffix ||
host.endsWith("." + suffix)`. Із простим `endsWith` будь-хто міг би назвати домен
`not-greenhouse.io` і ми прийняли б його за дошку Greenhouse.

**У переліку лише хости самої платформи.** Кастомний домен клієнта ATS
(`jobs.company.com`) дає `unsupported` - адреса про нього нічого не каже. Так само
`schema_org` не повертається ніколи: розмітку JobPosting видно лише з вмісту
сторінки, тому справжнє підтвердження дасть пробне читання в етапі 3.

| Суфікс хоста                            | Платформа   |
| --------------------------------------- | ----------- |
| `greenhouse.io`                         | greenhouse  |
| `lever.co`                              | lever       |
| `ashbyhq.com`                           | ashby       |
| `myworkdayjobs.com`, `myworkdaysite.com` | workday    |
| `peopleforce.io`                        | peopleforce |
| решта                                   | unsupported |

Звідки взяті домени - у коментарі до `PLATFORM_DOMAINS`: у Greenhouse офіційно
описаний лише `boards.greenhouse.io`, решта хостів перевірена запитами.

## Підказки для полів Add company

`suggestCompanyFields` розбирає одну вставлену адресу й віддає, що підставити в поля
модалки. Запитів у мережу немає: усе видно з рядка.

| Вставлено                  | Головний сайт | Назва  | Карʼєрна сторінка          |
| -------------------------- | ------------- | ------ | -------------------------- |
| `bosch.com`                | `bosch.com`   | Bosch  | -                          |
| `bosch.com/de/careers/jobs`| `bosch.com`   | Bosch  | `bosch.com/de/careers/jobs`|
| `about.gitlab.com`         | `about.gitlab.com` | Gitlab | -                     |
| `jobs.lever.co/spotify`    | -             | Spotify| `jobs.lever.co/spotify`    |
| `bosch.wd3.myworkdayjobs.com/External` | - | Bosch | та сама адреса           |

**Назва - передостанній лейбл домену**, з кроком назад на домені другого рівня
(`bosch.com.ua` - Bosch, інакше вийшла б «Com»). Список таких суфіксів короткий і
живе в коді: повний Public Suffix List оновлюється окремо від нас, а виграш від нього
тут - кілька рідких доменів. Абревіатури не розпізнаються: `bbc.co.uk` дасть «Bbc».

**Усе, що після домену, їде в поле карʼєрної сторінки.** Головний сайт обрізається до
домену, і без цього вставлений шлях просто зникав би. Наслідок: `bosch.com/de` теж
потрапить у карʼєрне поле, хоча це національна версія сайту - поля редаговані, і
користувач переносить адресу сам. Правило свідомо не вгадує за словами в шляху
(`careers`, `jobs`): такий список довелося б тримати й доповнювати, а вигоди - лише
на крайніх випадках.

**Адреса ATS не дає головного сайту.** `lever.co` сайтом Spotify не є, а вивести
`spotify.com` зі slug-а не можна: буває `.io`, `.ai`, інший slug. Поле лишається
порожнім - його заповнює користувач або, з етапу 5, Find pages. Підставити туди саму
адресу ATS теж не можна: тоді всі компанії з Lever виглядали б як один домен, і
попередження про однаковий домен втратило б сенс.

**Де в адресі ATS стоїть назва - залежить від платформи.** У Greenhouse, Lever і Ashby
це перший сегмент шляху, у Workday і PeopleForce - субдомен (`bosch.wd3.myworkdayjobs.com`).
Перелік доменів платформ лишається один - у `platform.ts`; `suggest.ts` бере в нього
суфікс через `platformHostSuffix`, щоб відрізнити лейбли компанії від лейблів платформи.
Адреса без slug-а (`jobs.lever.co`) назви не дає.
